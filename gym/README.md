# NeMo Gym environment — Escape from Red Hat

A NeMo Gym environment (Resources Server + tasks + scoring) for the same office-evacuation drill the app runs.
It is a **thin proxy over the app's TypeScript engine**: rollouts run the identical simulation, tool
validation and scoring as the live demo and the `npm run bench` benchmark. Nothing is reimplemented in Python.

- **Package:** `nemo-gym==0.6.0` (PyPI upload 2026-09-09; 0.7.0 is excluded by the hackathon's two-week reuse rule). It requires Python ≥ 3.13.14.
- **Ruleset 2 note (2026-10-17 evening):** the game moved to ruleset 2 — spreading fire, electrical failures on sliding doors, fire-alarm pull stations with a new `pull_alarm` tool, losses, and no time limit. The task rows in `data/` and the recorded `tests/dev-00-hero.calls.json` were generated for **ruleset 1** and must be regenerated (`npx tsx gym/make_tasks.ts`, then re-record the hero calls) before Gym runs are meaningful; `app.py` needs `pull_alarm` added to its tool routes.
- **Status:** see [Honest status](#honest-status) below. In short:
  - the environment, tasks and scoring run end to end through the real 0.6.0 classes;
  - the baseline-vs-final numbers are **not yet measured**;
  - prompt/harness improvement is **not RL**.

## What the environment is

| Gym concept | Here |
|---|---|
| **Task** | One seeded scenario from `data/scenarios/cases.{dev,test}.jsonl` (`escape-office-scenarios-v2`, CC BY 4.0). Each scenario has spawns, one or two spreading fires, maybe an electrical failure on a sliding door, Daniel's assistance preference, and labels (`solvable`, `expectLosses`). |
| **Tools** (10) | `observe`, `consult_plan`, `notify`, `plan_route`, `move`, `request_assistance`, `assist`, `check_in`, `verify_roster`, `pull_alarm` |
| **Session state** | One engine episode per Gym session (`SESSION_ID_KEY` cookie). It lives in the app server (`/api/gym/sessions/:id`), so it is isolated per rollout. |
| **Tool result** | JSON `{result, done, outcome, state}`. `result` is the engine's `ToolResult`: either ok, or an error code with a hint; invalid calls never change the world. `state` is a compact planner view, including `changes` since the last call. |
| **Clock** | Lockstep. The sim is frozen while the model thinks; after each call it advances until the planner has work again. Each call is one decision; the engine caps decisions (ruleset 1: 24; ruleset 2: 60 by default) and a stall guard ends runs with no progress. There is no gameplay time limit. |
| **Reward** (`verify`) | The engine's score. Ruleset 2: **+1** verified success (all three alive, checked in, roster verified, hazard reported by alarm or notify); **0** partial, incomplete or unresolved; **−1** everyone lost, or a critical violation (the same invalid call repeated ≥3 times after feedback, or ≥2 moves into known hazards). Stopping early is scored as `incomplete`. (Ruleset 1 also required the buddy escort when Daniel wanted one, and had `timed_out`.) |
| **Extra metrics** | `success`, `decisions`, `invalid_calls`, `recoveries`, `sim_time_s` (top-level numeric fields that Gym aggregates), plus `outcome_status`. |

Prompts are generated by the **same code the app uses** (`apps/server/src/prompt.ts`). Each task row's
`responses_create_params.input` has two messages:
- the system prompt for harness v1 or v2, plus a note on the multi-turn result format;
- the engine's initial planner view.

That view is deterministic, so `seed_session` reproduces the same state.

## Commands

Run from the repo root unless noted.

```bash
# 0. Python env (two-week-rule pin)
uv venv gym/.venv --python 3.13
uv pip install --python gym/.venv nemo-gym==0.6.0 httpx pytest

# 1. App server (engine + /api/gym). The planner provider is irrelevant here: Gym brings the model.
PORT=8791 PLANNER_PROVIDER=scripted npx tsx apps/server/src/index.ts

# 2. (Re)generate task rows from the published dataset
npx tsx gym/make_tasks.ts

# 3. Integration tests (real nemo-gym classes + live engine)
cd gym && ESCAPE_API_URL=http://127.0.0.1:8791 .venv/bin/python -m pytest resources_servers/escape_red_hat/tests -q

# 4. Start the Gym stack (head server + resources server + simple_agent + policy model). From gym/:
export ESCAPE_API_URL=http://127.0.0.1:8791
export PLANNER_API_KEY=...            # key for the policy endpoint (never on the command line)
.venv/bin/ng_run "+config_paths=[resources_servers/escape_red_hat/configs/escape_red_hat.yaml,resources_servers/escape_red_hat/configs/policy_model_openai_compatible.yaml]" \
  +policy_base_url=http://localhost:8000/v1 '+policy_api_key=${oc.env:PLANNER_API_KEY}' \
  +policy_model_name=nemotron-3.5-lightning +skip_venv_if_present=true
#   Hosted NVIDIA API Catalog instead (slow, dev only): +policy_base_url=https://integrate.api.nvidia.com/v1
#     +policy_model_name=nvidia/nemotron-3.5-lightning-30b-a3b ++policy_model.responses_api_models.vllm_model.chat_template_kwargs=null

# 5. Collect rollouts + scores (one file per harness; same cases, same config)
.venv/bin/ng_collect_rollouts +agent_name=escape_red_hat_simple_agent \
  +input_jsonl_fpath=resources_servers/escape_red_hat/data/test_v1.jsonl \
  +output_jsonl_fpath=results/test_v1_rollouts.jsonl +num_samples_in_parallel=8
.venv/bin/ng_collect_rollouts +agent_name=escape_red_hat_simple_agent \
  +input_jsonl_fpath=resources_servers/escape_red_hat/data/test_v2.jsonl \
  +output_jsonl_fpath=results/test_v2_rollouts.jsonl +num_samples_in_parallel=8
```

Each output row carries the `verify` response: `reward`, `success`, `decisions`, `invalid_calls`, `recoveries`, `sim_time_s`, `outcome_status` and `failure_reason`.

## Baseline-vs-final protocol (Gym bounty)

Task: a planner must coordinate a drill in which a route becomes blocked mid-evacuation, honouring a consent-based assistance arrangement and finishing with verified accountability.

1. **Baseline:** harness **v1**, which has the role, people, map and tools but no procedure.
2. **Final:** harness **v2**, which adds the explicit exercise procedure and error-recovery guidance; tool results are unchanged.
3. Use the **held-out test split** (`test_*.jsonl`). Its fire locations are structurally different from dev (see `data/scenarios/DATASET_CARD.md`). Use the same model, endpoint, sampling, `max_steps`, decision cap and number of repeats for both.
4. Report reward, success rate, invalid-call rate and recoveries for both, and the delta. Disclose the small N (16 cases × repeats).
5. **Ablation to isolate the change:** v2 minus the recovery paragraph, and v2 minus the assistance paragraph (TODO if time allows).

Development tuning uses only `dev_*.jsonl`. The test split is not used to edit prompts.

## Honest status

**Verified here (2026-10-17):**
- `nemo-gym==0.6.0` installs on Python 3.13.14.
- `EscapeResourcesServer` subclasses the real `SimpleResourcesServer`.
- `tests/test_app.py` passes against a live app server. It covers:
  - `seed_session` → 18 replayed calls → `verify`, giving **reward 1 / success** on `dev-00-hero`. The calls come from the scripted fixture, not a model; this checks plumbing.
  - Invalid calls coming back as model-visible `INVALID_ARGUMENT` errors.
  - Per-session isolation.
  - Early stop scored as incomplete.
- `ng_run` starts all 3 servers (resources server, `simple_agent`, `vllm_model`) with these configs. The `vllm_model` → hosted Catalog leg returns native function calls (probe below).
- The Gym session API has 8 vitest tests, including the scripted policy reaching reward +1 through it.

**Not yet done / not verified:**
- A rollout with the real model. See the transcript note below; the hosted endpoint is slow.
- Baseline-vs-final numbers on the test split. These need our self-hosted vLLM for practical latency.

**Other caveats:**
- This is a **prompt/harness improvement, not RL**. No model weights change. NeMo RL GRPO needs 8× 80 GB GPUs per NVIDIA's tutorial, which we don't have.
- Whether a harness improvement qualifies for the Gym bounty is **pending organizer confirmation**.
- The live app uses a stateless per-decision prompt (system + current view). The Gym environment is the multi-turn variant (`simple_agent` appends tool outputs to the conversation), with a compact state so 24 steps fit in a 16K context. Results from the two harness styles are reported separately and not mixed.
